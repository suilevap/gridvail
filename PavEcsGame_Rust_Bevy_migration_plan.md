# PavEcsGame → Rust / Bevy: оценка и план миграции

Дата: 20 сентября 2026 года. Основание: ветка `master`, commit [bc0b449f68d953861932214b85110f99925d886a](https://github.com/suilevap/PavEcsGame/tree/bc0b449f68d953861932214b85110f99925d886a), от 27 января 2026 года.

## 1. Оценка

**Да, существующая ECS-архитектура заметно упрощает перенос. Проект — хороший кандидат для Rust/Bevy.** Компоненты, небольшие системы, целочисленная карта и отдельные алгоритмы уже дают подходящую основу.

Основная работа — переписать игровые системы на Rust, заменить собственную ECS-инфраструктуру средствами Bevy и сохранить порядок изменения состояния. Переосмысливать игру целиком не потребуется.

По сложности: компоненты и математика — низкая; интеграция систем — средняя; точное сохранение симуляции, коллизий и кэшей — наиболее трудная часть.

**Предварительный объём для одного разработчика, знакомого с Rust/Bevy:**

- Первый вариант «карта, игрок, движение, стены» — 2–4 полных рабочих дня при небольшом числе проблем с исходным запуском.
- Основной пример с FOV, светом, привязанным объектом, проверками и оконным выводом — 10–18 рабочих дней.
- Для календарного планирования с резервом — примерно 3–5 рабочих недель.
- Отдельный Tetris в текущем объёме — дополнительно 2–4 дня после готовности общей основы.

Это экспертная оценка, не результат пробного порта. Она предполагает сохранение текущих возможностей, без разработки новой графики, механик или редактора. Освоение Rust по ходу работы увеличит срок.

Анализ выполнен по исходникам, структуре проектов и закреплённой версии EcsLite. Исходная игра не запускалась, сборка и бенчмарки не проводились: в среде анализа нет .NET и Rust SDK.

## 3. Границы первой миграции

Основной результат: **тот же клеточный пример в окне Bevy с символьной графикой**, собственными FOV и освещением.

Включить:

- загрузку существующих карт и создание шести типов объектов;
- управление игроком и случайное движение врагов;
- токены действий, движение, трение и разрешение коллизий;
- направления и относительное положение привязанного объекта;
- удаление объектов и согласованность карты;
- автотайлинг стен, FOV, Known/Visible, статический и динамический свет;
- текущие символы и палитру;
- запуск и проверку на macOS и Windows.

`DamageOnCollisionSystem` есть в коде, но отключён в основном контейнере. Его включение не считать обязательным для достижения текущего поведения. То же относится к закомментированным альтернативным рендерам.

Tetris переносить отдельно. В нём уже есть перемещение, поворот и закрепление фигуры при блокированном обязательном движении. Удаление строк отключено в контейнере; автоматическое падение не реализовано в активном цикле. Доработка полноценного Tetris — дополнительная задача. [Tetris][tetris], [MoveSystem Tetris][tetris_move].

## 4. Целевая структура

Для такого размера достаточно **одного Cargo-пакета с библиотекой и двумя возможными bin**, без отдельного ECS-фреймворка.

| Модуль / путь | Назначение |
|---|---|
| `src/lib.rs` | Регистрация игровых плагинов |
| `src/bin/game.rs` | Основной оконный пример |
| `src/components.rs` | Игровые компоненты |
| `src/map/` | Grid, загрузчик, создание объектов, tile rules |
| `src/simulation/` | Токены, команды, движение, коллизии, привязки, удаление |
| `src/vision/` | Алгоритм FOV, интервалы, кэши, Known/Visible |
| `src/lighting/` | Карты света, смешивание, инвалидация |
| `src/presentation/` | Композиция клеток, палитра, вывод Bevy |
| `tests/fixtures/` | Входы и эталонные результаты |
| `assets/maps/`, `assets/rules/` | Существующие txt |
| `src/bin/tetris.rs`, `src/tetris/` | Опциональный второй пример |

Начать с одного основного игрового `World`. Дополнительные миры, которые сейчас строит EcsUniverse по связям типов, не переносить автоматически. Разделение данных через компоненты, ресурсы и запросы здесь достаточно; это не требует вмешательства в внутренний render world Bevy.

Алгоритмы карты, FOV и интервальных вычислений оформить обычными Rust-функциями и структурами. Их можно тестировать без окна. Игровые системы используют Bevy ECS напрямую.

На дату анализа документация показывает **Bevy 0.19.1**. Для первой итерации закрепить проверенную версию и `Cargo.lock`, не совмещать порт с обновлением движка. [Bevy API](https://docs.rs/bevy/latest/bevy/).

## 5. Что переносится, а что заменяется

| Сейчас | В Rust / Bevy | Примечание |
|---|---|---|
| Компоненты C# | `#[derive(Component)]` | Большинство — простые структуры |
| Int2 и PositionComponent | `IVec2` + `GridPosition` | Игровые координаты оставить целочисленными |
| SpeedComponent | `GridVelocity(IVec2)` | Это перемещение за проход, не м/с |
| EcsReadonlySpec / EcsSpec | `Query<&T>` / `Query<&mut T>` | Крупные параметры группировать только при необходимости |
| Inc / Exc / Opt | Query data, With, Without, Option | Optional-доступ не добавляет компонент |
| EcsEntityFactorySpec | Spawn-функции, наборы компонентов | Factory spec сам по себе не означает наличие всех компонентов |
| EcsUniverse и union-find типов | Один World, Resources, SystemSets | Собственный аналог не нужен |
| EcsPackedEntityWithWorld | `Entity`, `Option<Entity>` | Проверять актуальность ссылки; ID не является владением |
| MapData<T> | `Grid<T>` с `Vec<T>` | Индекс `y * width + x`, явные границы |
| Карта занятости | Resource с `Grid<Option<Entity>>` | Хранит коллайдеры, не все отображаемые объекты |
| CommandToken / WaitCommandToken | Постоянный компонент бюджета | Сохранить правило пополнения |
| NewPositionComponent | Явный запрос изменения позиции | Различать отсутствие запроса и удаление с карты |
| SystemHasMoreWorkTag / SystemRef | Resource состояния симуляции | Сущности, представляющие системы, не нужны |
| CollisionEvent-entity | Буфер результатов прохода | Очистка после всех потребителей |
| AreaResultComponent | Владеющий буфер / resource по назначению | Не переносить общий интерфейс ради самого интерфейса |
| ConsoleRenderSystem | Оконный вывод клеток | Композицию символов сохранить |
| RenderItemCommand-entity | Изменённые клетки в буфере | Не создавать сущность на каждую перерисовку |
| SynchronizationContext / WorkQueue | Синхронная стартовая загрузка | Для маленьких карт этого достаточно |
| PerfTimer / ActionSystem | Диагностика времени систем | Измерять симуляцию отдельно от рендера |

**Особенность фабрик:** методы `Add` принимают nullable-компоненты и пропускают `default`, если это `None`. Перевод такой записи в Bundle со всеми полями изменит состав сущностей. Сначала выписать фактические наборы каждого spawn-case. Вложенные factory specs объединяют доступные типы/миры, но не автоматически создают «родительские» компоненты. [Фабрики объектов][spawn], [Add-overloads][entity_ext].

Обычные компоненты Bevy требуют `Send + Sync + 'static`; для текущих числовых данных и владеющих буферов это естественно. Общие изменяемые объекты C# переносить с явным владельцем. Например, враги сейчас получают ссылку на один `Random(42)`, поэтому независимый RNG на каждом враге изменит последовательность действий. [Component](https://docs.rs/bevy/latest/bevy/ecs/component/trait.Component.html).

## 6. Критичные различия поведения

### 6.1. Порядок систем и отложенные изменения

Сейчас системы выполняются последовательно, а изменения пулов доступны следующим системам. В Bevy порядок нужно задать явно. Сам по себе конфликт записи запрещает параллельный доступ, но не определяет, какая система выполнится первой.

Для первой версии использовать явно упорядоченные группы и `.chain()` там, где результат нужен следующей системе в том же проходе. Не пытаться сразу распараллелить движение и карту.

`Commands` откладывает структурные изменения. При стандартной конфигурации Bevy вставляет применение отложенных команд между зависимыми системами. Для собственного расписания проверить эти границы интеграционным тестом. Не использовать `chain_ignore_deferred` на пути «создали компонент → прочитали компонент». Изменения, сделанные через Commands, нельзя считать доступными внутри той же системы. [ApplyDeferred](https://docs.rs/bevy/latest/bevy/ecs/schedule/struct.ApplyDeferred.html), [расписание](https://docs.rs/bevy/0.19.1/bevy/ecs/schedule/trait.IntoScheduleConfigs.html).

### 6.2. Удаление последнего компонента

В закреплённой версии EcsLite `EcsPool.Del` автоматически удаляет сущность, когда у неё закончились компоненты. Этим пользуются временные render commands, события и результаты света.

В Bevy удаление компонента оставляет сущность существовать. Поэтому временные объекты нужно либо явно despawn, либо заменить буфером/resource. Простая замена `Del<T>` на `remove::<T>` даст накопление пустых сущностей. [EcsLite, закреплённый исходник](https://github.com/Leopotam/ecslite/blob/4622c76134cac0c280f5878be3d645005ab5a1fa/src/components.cs), [Commands](https://docs.rs/bevy/latest/bevy/ecs/system/struct.Commands.html).

### 6.3. У NewPosition три состояния

| Исходное состояние | Смысл |
|---|---|
| Компонента нет | Нет запроса |
| Компонент есть, Value содержит позицию | Переместить / разместить |
| Компонент есть, Value = null | Убрать с карты |

При постоянном компоненте это можно представить так:

```rust
enum PositionChange {
    MoveTo(IVec2),
    RemoveFromMap,
}

#[derive(Component, Default)]
struct PendingPosition(Option<PositionChange>);
```

Один `Option<IVec2>` для всей этой задачи недостаточен: он объединит два разных отсутствия.

### 6.4. Коллизии зависят от алгоритма, не только от компонентов

В `UpdatePositionSystem` сначала выполняется `PlaceToNewPos`, затем `RemoveFromMap`, потом сохранение предыдущей позиции и применение новой.

Отсюда следуют правила:

- в момент проверки старые клетки движущихся объектов ещё заняты;
- обмен местами двух коллайдеров блокируется;
- вход в клетку уходящего коллайдера тоже блокируется в этом проходе;
- при конкуренции за одну свободную клетку победитель зависит от порядка обработки;
- заблокированный ход не должен освобождать старую клетку.

Сохранить это как исходный контракт. Не начинать с «сначала очистим все старые позиции»: получится другая механика.

Для спорных перемещений ввести явный стабильный порядок, например номер создания. Если он расходится с наблюдаемым порядком EcsLite, записать это как осознанное изменение, а не заявлять полную идентичность.

Реализация: собрать заявки в переиспользуемый буфер → зарезервировать разрешённые цели → освободить старые клетки только принятых заявок → обновить компоненты. Для первой версии допустима одна небольшая exclusive-система с `&mut World`, если так проще обеспечить согласованность. Остальные системы остаются обычными Query-системами. [UpdatePositionSystem][position].

### 6.5. Координаты и ссылки

Сохранить игровую ось Y вниз. Инвертировать её только при переводе в экранные координаты Bevy. Не заменять целочисленную модель через Transform.

`GetSafePos` оборачивает координаты коллайдеров по карте. В Rust использовать `rem_euclid`; исходное выражение с однократным прибавлением размера не покрывает произвольно большие отрицательные смещения. FOV, напротив, считает выход за границы препятствием. Не превращать все операции с картой в одинаковый torus-wrap.

Привязанные объекты могут не иметь Collider. Они не занимают отдельную клетку в occupancy-grid. Ссылки на исчезнувшего родителя проверять через ECS; политику удаления/сохранения ребёнка задать явно. Автоматическое удаление и Transform-иерархия не являются точной заменой текущему `RelativePositionSystem`. [Карта][map], [привязки][relative].

### 6.6. FOV и свет — собственные игровые алгоритмы

FOV здесь выдаёт дробную видимость через перекрытие угловых интервалов. Замена готовым бинарным FOV изменит результат на углах и у стен.

Сначала перенести `FieldOfViewComputation`, квадратные кольца и `RangesCollectionV2`. Связный список можно заменить переиспользуемым Vec интервалов, сохранив правила объединения и круговой границы 0/1. Проверить алгоритм до оптимизации.

Стены препятствуют зрению через проверку отсутствия Speed у объекта в occupancy-grid. Выделить эту семантику в `BlocksVision`, назначив её тем же объектам. Нельзя автоматически сделать любой Collider непрозрачным.

Освещение — CPU-карта значений, типов света и палитры. Его нужно сохранить; штатные PointLight/PBR не дают эквивалентного результата. У текущего смешивания есть насыщение до 255, суммирование совместимых типов и выбор более сильного несовместимого источника. Для совпадения также важен порядок источников. [FOV][fov], [алгоритм][fov_algorithm], [свет][light].

## 7. Расписание симуляции

**Разделить кадр окна, проход симуляции и пополнение бюджета действий.** Это три разных события.

Сейчас `TurnManager.CurrentPhase` зависит от флагов незавершённой работы; часть систем выставляет их до обработки, часть — по факту выполненной работы. Следующий проход может требоваться для окончательного снятия флага. Поэтому перед упрощением нужны трассы нескольких типичных действий. [TurnManager][turn].

Правило пополнения токенов тоже не равно «один ход в секунду»: бюджет пополняется, когда закончились все токены, **или** прошло больше секунды с прошлого пополнения. Значение присваивается заново, а не добавляется к старому. [CommandTokenDistributionSystem][tokens].

Предлагаемый порядок:

| Участок | Действия | Условие перехода |
|---|---|---|
| Кадр окна | Считать ввод, обновить часы | Не менять мир из обработчика ввода |
| Подготовка действий | Проверить пополнение бюджета; в допустимой фазе подготовить команды игрока и NPC | Сохранить ограничения токенов |
| Проход симуляции | Применить команды; направление по скорости; заявки движения; трение | Не считать dt множителем клеточной скорости |
| Разрешение | Привязки; коллизии; применение позиций; обработка удаления | После commit карта согласована |
| Продолжение | Проверить оставшуюся скорость, привязки, заявки и удаление | Пока есть работа — ещё проход, без нового чтения клавиатуры |
| Представление | FOV → свет → Known/Visible → композиция клеток | На согласованном состоянии мира |
| Завершение | Очистить данные с закончившимся сроком жизни | После всех их потребителей |

Начать с поведения, близкого текущему последовательному циклу. Затем отделить принятие новых команд от доведения уже принятых действий до завершения. Влияние такого упрощения на частоту решений NPC и момент ввода зафиксировать в тестах.

Количество проходов за кадр ограничить настраиваемым пределом. Если работа осталась, продолжить её в следующем кадре, сохранив состояние. В диагностическом режиме показывать причину отсутствия сходимости. Нельзя зависать в бесконечном цикле.

Клавиатуру читать один раз на кадр. Команду хранить до допустимого момента обработки; повторы удержанной клавиши задавать явно. Это устраняет существующее место, где консольная клавиша читается до проверки Simulation-фазы и может потеряться. Изменение ввода отметить отдельно от сохранения игровой механики.

Временные коллизии удобнее хранить в resource-буфере на один проход. Если применяются Bevy Messages, задать потребителей и обслуживание буфера для собственного расписания: срок сообщения не должен случайно зависеть от частоты рендера. [MessageReader](https://docs.rs/bevy/0.19.1/bevy/ecs/message/struct.MessageReader.html).

## 8. Поэтапная реализация

### M0. Зафиксировать исходное поведение — 0,5–1 день

- Собрать Lite из указанного commit с его submodule на машине с .NET 10.
- Проверить загрузку `map1.txt`, движение, свет и управление.
- Сделать небольшой режим вывода состояния после прохода/завершённого действия.
- Записывать позиции, скорость, бюджеты, occupancy, привязки и результаты FOV/света.
- Для сравнения движков записывать выбранные NPC-команды: одинаковый seed не гарантирует одинаковый поток случайных чисел в C# и Rust.
- Выделить расхождения исходника, которые надо исправить, из поведения, которое сохраняется.

**Готово:** есть воспроизводимые входы и эталонные результаты; подтверждён фактический запуск исходника. Если запуск сломан, сначала устранён конкретный блокер и записан минимальный патч.

### M1. Создать основу Bevy — 0,5–1 день

- Один пакет, основное приложение и библиотека логики.
- Закрепить версию Bevy.
- Создать окно, камеру 2D и ресурсы игры.
- Явно задать расписание и состояния загрузки/готовности/ошибки.
- Добавить запуск симуляции в тестах без окна.

**Готово:** приложение открывается и закрывается; тест может вручную выполнить один проход.

### M2. Перенести карту, типы и spawn — 1–2 дня

- GridPosition, GridVelocity, игровые маркеры, бюджет и запрос изменения позиции.
- Grid с Vec и Option<Entity>, проверка размеров и индексов.
- Загрузка всех пяти карт и четырёх правил.
- Корректная обработка UTF-8 BOM, CRLF/LF и Unicode: ширину символов правил считать через chars, не через количество байтов.
- Повторить фактические составы Wall, Player, Enemy, Electricity, Light, Acid.
- Добавить минимальный вывод карты и игрока.

Для текущих файлов достаточно синхронной загрузки в Startup с явной ошибкой. Асинхронный AssetLoader добавлять при реальной необходимости; собственный SynchronizationContext не переносить.

**Готово:** каждая карта загружается с правильными размерами и объектами; маленький тест spawn проверяет точный состав компонентов.

### M3. Перенести команды, движение и коллизии — 2–4 дня

- Пополнение бюджета, приём команд, случайное движение.
- Направление по скорости, создание заявки, целочисленное трение.
- Разрешение конфликтов по правилам раздела 6.4.
- Стабильный порядок конкурирующих заявок.
- Проверки на границах, заблокированные ходы и отсутствие бюджета.
- Управление несколькими проходами симуляции.

**Готово:** игрок и враги двигаются; стены блокируют; map/entity-state совпадают; один ввод не применяется несколько раз из-за дополнительных проходов.

Первый рабочий вариант можно получить до завершения всех краевых тестов M3 — отсюда оценка 2–4 дня на начальную демонстрацию.

### M4. Привязки и удаление — 1–2 дня

- RelativePosition, направление и ссылка на родителя.
- Позицию привязанного объекта вычислять относительно принятого положения родителя, учитывая исходную семантику проходов.
- Проверить блокированное движение, поворот на месте и wrap родителя.
- Отделить снятие объекта с карты от его удаления из ECS.
- Добавить очистку временных сущностей либо заменить их буферами.
- Перенести инварианты VerifyMapSystem.

**Готово:** привязанный объект после завершения действия находится в нужной клетке; удалённые объекты не оставляют occupancy и stale-ссылок.

### M5. FOV, Known/Visible и свет — 2–3 дня

- Перенести интервальный FOV и порог видимости 0,1.
- Сохранить Known после исчезновения Visible.
- Перенести falloff, типы света, насыщение и палитры.
- Сохранить разделение статического слоя и динамического добавления.
- Добавить явные версии входов кэша.
- Проверить добавление, удаление и перемещение источника и препятствия.

**Готово:** результаты на фиксированных сценах совпадают с утверждёнными эталонами; кэш обновляется при изменении входов.

### M6. Завершить оконный вывод — 2–3 дня

- Перенести выбор символа по Depth и правила отображения известных/видимых клеток.
- Вне Visible не показывать движущихся акторов только потому, что клетка Known.
- Сохранить символы стен, направлений, источников и границы неизвестного.
- Начать с постоянных объектов отображения клеток; обновлять изменённые значения.
- Для исходных 1 920 клеток сначала измерить обычный текстовый/спрайтовый вариант.
- Подключить моноширинный шрифт или атлас со всеми используемыми Unicode-глифами.
- Настроить масштабирование и преобразование Y; обеспечить предсказуемую палитру.

Не переносить консольные вызовы установки курсора и группировку Console.Write. Не писать специальный GPU render pipeline до измерения обычного варианта.

**Готово:** текущую карту удобно исследовать в окне; символы не пропадают, клетки не искажены, движение не оставляет следов.

### M7. Проверить и завершить — 1–2 дня

- Прогнать матрицу ниже.
- Сравнить игровые результаты по командам и завершённым действиям, а не по номерам кадров.
- Проверить release-сборки на macOS и Windows.
- Замерить отдельно симуляцию, FOV, свет, подготовку вывода и общее время кадра.
- Проверить стабильность числа сущностей и объёма временных буферов.
- Записать запуск, управление, известные изменения поведения и ограничения.

**Готово:** основной пример воспроизводит согласованные возможности исходника; отличия перечислены; нет зависимости от FPS и накопления временных сущностей.

**Сумма M0–M7: 10–18 рабочих дней.** Переоценить остаток после M3: это главный этап проверки архитектурного риска.

## 9. Отдельно исправить найденные слабые места

Это наблюдения по коду; проявление в запущенной игре требует проверки.

| Место | Наблюдение | Решение в порте |
|---|---|---|
| FieldOfViewSystem | Ключ кэша — позиция и запрос; изменение препятствий не входит | Добавить версию геометрии препятствий |
| LightRenderSystem | Локальная переменная rev считывается, но в currentVersion не используется; версия вычисляется XOR по ID | Явная dirty-версия статического слоя и его источников |
| LightRenderSystem | При совпадении нулевых версий первый пересчёт может не произойти | Отдельный флаг валидности; инвалидировать при загрузке карты |
| LightSourceSystems | Запрос игрока переписывает radius после запроса света на той же сущности | Проверить случай разных радиусов; определить общий max или отдельные результаты |
| TileSystem | Маски вычисляются с удалением TileComponent и передачей маски соседям | Двухфазный расчёт масок по неизменяемому набору тайлов |
| KeyboardMoveSystem | Ключ читается до проверки фазы | Сохранение pending input |
| MapData | Выделяется Width+1 × Height+1, но действительный диапазон меньше | Явный размер без неявной дополнительной границы |
| PlayerFieldOfViewSystem | Проверка угла зрения закомментирована | Сохранить текущую круговую видимость; конус — отдельная механика |

Для кэша FOV достаточно позиции, радиуса, размеров карты и версии препятствий. Для статического света дополнительно учитывать изменения позиции/параметров, состава источников и версии их FOV. Удаление последнего источника тоже должно инвалидировать слой.

Исправления, меняющие результат относительно исходника, снабдить отдельными ожидаемыми результатами. Не выдавать исправленный результат за буквальное совпадение.

## 10. Минимальная матрица проверок

| Сценарий | Что проверять |
|---|---|
| Все пять карт | Размеры, координаты, число и типы объектов |
| Правила символов | BOM/Unicode, все используемые направления и маски стен |
| Обычный ход | Позиция, скорость после трения, расход бюджета |
| Нет токена | Команда не выполняется досрочно |
| Пополнение | Все токены исчерпаны; таймаут; токены ещё остались |
| Два претендента | Одна целевая клетка, один победитель по заданному порядку |
| Обмен местами / следование | Сохранён консервативный контракт занятости |
| Границы | Все стороны карты; большие отрицательные смещения |
| RemoveFromMap | Отдельно от отсутствия заявки и от despawn |
| Привязка | Поворот, движение, блокировка, wrap, исчезновение родителя |
| FOV | Пустая область, угол стены, закрытая комната, край карты |
| Свет | Ноль источников; статический + динамический; изменение типа/радиуса; удаление |
| Known/Visible | Исследованная клетка остаётся Known; NPC за пределами обзора скрыт |
| Инвалидация | Неподвижный наблюдатель при изменении препятствия |
| Несколько проходов | Ввод применяется один раз; события не исчезают раньше потребителей |
| Длинный прогон | Число временных сущностей не растёт после 1 000 проходов |
| Разная частота кадров | При одинаковых командах и времени состояние игры совпадает |

Целочисленные данные сравнивать точно. Для дробной видимости сначала зафиксировать допустимую погрешность по перенесённому алгоритму; особенно проверить значения около порога 0,1 и преобразование яркости в byte.

Для производительности достаточно исходной карты и одной увеличенной сцены. Не начинать с обещания нулевых аллокаций: сначала переиспользовать основные буферы и измерить. В текущей схеме есть полноразмерный float-буфер на источник и проходы по всей карте; оптимизация по радиусу/области нужна только при росте сцены.

## 11. Tetris после основной миграции

Выделить отдельный bin и повторно использовать GridPosition, палитру и клеточный вывод.

1. Перенести FiguresData и побитовые операции в u32 / массив из четырёх строк.
2. Перенести MapComponent в явно изменяемый resource: C# сейчас меняет массив внутри readonly-доступа, что не эквивалентно Rust `&T`.
3. Перенести движение, поворот и закрепление фигуры.
4. Проверить границы перед сдвигами: C# маскирует величину shift, а прямой перенос выражения в Rust может дать ошибку/другое поведение.
5. Убрать создание сущностей клеток каждый кадр; заполнять общий буфер отображения.
6. Сохранить текущий активный набор механик.

Оценка — 2–4 рабочих дня. Автоматическое падение, исправление/включение удаления строк, счёт и game over оценивать отдельно. [TetrisMapUtils][tetris_utils].
